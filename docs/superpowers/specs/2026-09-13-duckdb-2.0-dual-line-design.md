# DuckDB 2.0: the dual-line contract

**Status:** design approved by Teague in five sections, 2026-09-13; awaiting review of this
document before the implementation plan.
**Decisions taken first-hand:** posture "dual-line now"; 1.5 sunset "keep 1.5.5 one release
after the flip, then drop"; approach A, "registry-mirrored dual line".

## What is true today

- The community registry builds every extension at the default in `build.yml` (`v1.5.5`) and,
  when a descriptor carries `ref_next`, at the version in `build_next.yml` (`v2.0-cyanoptera`),
  with `require_ref_next: true`. duck_block_utils' descriptor has carried `ref_next = ref`
  since 3.1.0; the registry's prerelease leg passed on every platform for 3.2.0 (#2687).
- Our own canary builds against the 2.0 line only on pushes to `main` and on dispatch. It is
  green on `v2.0-cyanoptera`, including the linux_amd64 leg that runs the test suite.
- The code compiles on both lines through `src/include/duckdb_compat.hpp`, which detects
  features by `__has_include` of a header, then gates a group of shims on one macro.
- DuckDB has a `v2.0-cyanoptera` release branch and no `v2.0.0` tag. The registry keeps an
  older line alive only through a codename key in the descriptor plus a dedicated workflow;
  that exists for 1.4 (`andium:`, 73 descriptors) and not for 1.5.
- The fleet has a 21-class catalogue of 2.0 changes in duckdb_markdown's
  `docs/duckdb_v2_migration.md`; duckdb_mcp's `feat/duckdb-v2-compat` carries the fleet-standard
  shim (per-change member probes, tag dispatch, C++11-safe).
- markdown's sweep (2026-09-13): the constructor `ConstantExpression(const Value &)` is deleted
  on 2.0; call sites exist in webbed (1), yaml (11), zim (1), func_apply (4), sitting_duck (5),
  markdown (1, fixed). None of those descriptors carried `ref_next`, so the registry has never
  built them on the 2.0 line. duck_block_utils has zero such calls.

## 1. CI shape

Three build jobs in `MainDistributionPipeline.yml`:

| job | version | ci-tools | when | role |
|---|---|---|---|---|
| `duckdb-stable-build` | `v1.5.5` | `v1.5-variegata` | every push and PR | the artifacts our releases attach |
| `duckdb-next-build` | `v2.0-cyanoptera` | `main` | every push and PR, full matrix, tests on linux_amd64 | the registry's next line; a PR is not green until it passes |
| `duckdb-main-canary` | `main` | `main` | push to `main`, dispatch | advisory, the line beyond 2.0 |

`duckdb-next-build` is today's canary with its `if:` gate removed and renamed. The concurrency
group keeps `event_name` in its key so a dispatch cannot cancel a push run. `code-quality-check`
stays on the stable line. CI cost per PR roughly doubles; the lever if that matters is
`exclude_archs` on the next job, never the gate.

## 2. Pin rule and the assertion job

The rule generalises from "pin equals the shipped tag" to **"pin equals the registry's default,
and the workflow ships every line the registry builds."**

`duckdb-pin` resolves community-extensions `main` to a sha once and reads two values at that
sha: the default in `build.yml` and the version in `build_next.yml`. It asserts:

1. the `duckdb` submodule pin equals the peeled commit of the registry default's tag (`^{}`
   with a fallback for lightweight tags; both kinds exercised against real tags);
2. the typed constant `DUCKDB_VERSION` equals the registry default (the constant remains as the
   repo's statement of intent, checked against the authority rather than against itself);
3. at least one build job ships `duckdb_version: <default>` and at least one ships
   `duckdb_version: <next>`.

Degraded paths: an unreachable registry is a `::notice` and the summary line says the registry
assertions were not made, with only assertion 1 against the local constant run; a fetched file
that does not parse is a failure, because that is the check being wrong about the world. Tag
resolution itself fails hard: it is git protocol against the host the runner is on.

## 3. Descriptor and flip mechanics

Standing rule: every descriptor bump sets `ref_next = ref`, so one commit is proven on both
lines before it is served on either.

Flip day is driven by the registry, not a calendar:

1. The registry changes `build.yml`'s default to `v2.0.0` and, following the 1.4 precedent,
   adds `build_variegata.yml` and a `variegata:` key.
2. `duckdb-pin` goes red on the next run and names the new default and next versions.
3. One PR here: submodule to the `v2.0.0` tag; stable job to `v2.0.0` with ci-tools on the 2.0
   branch; next job to whatever `build_next.yml` now names; canary stays on `main`; the 1.5.5
   build becomes `duckdb-legacy-build`, kept for exactly one duck_block_utils release.
4. That release's descriptor sets `ref` and `ref_next` to the 2.0-tested commit and `variegata:`
   to the same commit, if the registry has added the key. If it has not, the 1.5 track ends at
   the last 1.5 build the registry served, and the release notes say so. We cannot create the
   track ourselves.
5. The following release drops the legacy job and the 1.5-only compat paths, and this record
   is updated with which release that was.

## 4. Code and tests

One-time audit against the 21-class catalogue, aimed at the classes a green build cannot see:

- **Feature probes, not proxy headers.** Replace the three `__has_include` gates and their group
  macros with per-change member probes in the fleet-standard form (mcp's header). DuckDB has
  backported a header (`identifier.hpp`) to the 1.5 branch without its signature change, so a
  header's presence can select the new API on a DuckDB that has the old one. We are safe today
  only because the pin is the exact tag.
- **Class 13, fallible scalar functions.** v2.0 enforces a contract 1.5 already consults:
  a scalar function that can throw during execution must call `SetFallible()`, else the throw
  is rewritten as an `INTERNAL Error` on 2.0. Seven pandoc functions are marked. The audit
  follows throwing helpers transitively (validation, builders constructing maps from user keys,
  `Value::GetValue` on user data), marks precisely (a handler that swallows is not fallible),
  and adds error tests that expect the exception's **type prefix**, since a bare-substring
  `statement error` passes on both the correct and the mis-declared form. Each test is checked
  in both directions.
- **Class 11.** 177 `ScalarFunction(...)` constructions; any that thread `nullptr` positionally
  past `bind` move to setters (`SetStability()` exists on both lines).
- **Not applicable, with the grep that established each:** class 7 (`GetAlias` /
  `capture_argument_aliases`: none), class 18 (`TableFunction(` / `SetCardinality`: none), class
  19 (`->` in macro SQL: none), class 21 (COPY options: none).
- **Standing protection.** `duckdb-next-build` runs the suite on 2.0 for every PR; the audit is
  the catch-up.

## 5. Fleet rollout

One pass per repo, four changes that answer one question, "is this extension built and tested
on the line the registry ships next":

1. the pin rule (section 2, job copied verbatim, extension name changed);
2. `duckdb-next-build` on PRs (section 1);
3. `ref_next = ref` in the descriptor on its next bump;
4. the `ConstantExpression` shim (markdown's `CompatConstant`, probe on `FromValue`, c86abc0)
   where the deleted constructor is called.

Order: fold sections 1 and 2 into duck_block_utils PR #33 so the reference is final before
anyone copies it. The five PRs this session opened (yaml #52, duck_tails #57, mcp #88,
sitting_duck #125, webbed #155) get the same plus the shim where call sites exist. markdown,
panduck and zim receive the sha and the change list and act on Teague's word in their own
sessions. `ref_next` registry PRs for repos without sessions are opened only after that repo's
next job is green, since a failing `ref_next` blocks the whole descriptor.

Expected and intended: the first run of the next job is red in webbed, yaml and zim. That is
the finding the rule exists to produce.

## Out of scope

catalogue; mcp's branch is the reference). Whether markdown ships v1.9.0 with a red prerelease
leg or cuts v1.9.1 (Teague's call in that session). The registry's own timing.
